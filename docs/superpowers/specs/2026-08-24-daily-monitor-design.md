# 每日监控自动化 — 设计说明

**日期**：2026-08-24

**状态**：设计已确认，待实施计划

**目标**：把现有“每日触发扫描 + 人工周检”收敛为一个工作日自动运行的“每日监控”，保留周检中有价值的正式披露核验、优先级判断和完整性检查，同时取消重复、繁琐的人工周检。

---

## 1. 背景与问题

当前体系包含两个相邻但分离的流程：

1. `tools/trigger_scanner.py` 每日检查价格区间和登记事件，结果写入 `reports/trigger-scan/`；
2. `/weekly-review` 每周联网核验重点标的、分配 P0/P1/P2、检查 thesis/看板/台账缺口，结果写入 `reports/weekly-check/`；
3. Pages 再把两份 latest 报告组合成“监控与周检”。

这造成三个问题：

- 同一标的和同一触发原因容易在扫描与周检中重复出现；
- 正式披露和研究完整性缺口要等到周检才发现；
- 每周需要人工发起、联网查证并整理一份与每日扫描重叠的报告。

新系统将两者整合为一个自动化日报，但仍保持“机器监控”和“投资决策”的边界。

---

## 2. 目标与非目标

### 2.1 目标

1. 周一至周五每天 17:30（`Asia/Shanghai`）自动运行；周末不运行。
2. 自动检查价格条件、登记事件、A/H/美股正式披露，以及本地研究体系的完整性缺口。
3. 仅对增量变化调用 DeepSeek，判断 P0/P1/P2、论文影响和下一步研究流程。
4. Pages 最终只展示一个活动入口：“每日监控”。
5. 报告按业务事实分为“价格监控”“财报与正式披露监控”“其他监控”三部分，避免按技术阶段重复陈述。
6. 保留历史周检和历史触发扫描文件，但停止继续生成周检。
7. 在单个数据源或 DeepSeek 故障时，仍尽可能产出可用的降级报告。

### 2.2 非目标

1. 不自动给出买入、卖出、加仓、减仓或仓位结论。
2. 不自动修改 thesis 健康度、看板状态、台账状态、组合或触发规则。
3. 不进行全网新闻搜索；一期只使用指定正式披露源。
4. 不把 PDF、公告正文、模型输入上下文或完整提取文本提交进仓库。
5. 一期不对扫描版 PDF 做 OCR；只标记待人工确认。
6. 不用每日监控替代 `/earnings-review`、`/news-pulse`、`/thesis-tracker`、`/thesis-drift` 或 `/portfolio-review` 等深度流程。

## 3. 用户可见产品形态

### 3.1 统一命名

- GitHub Actions、Pages 导航、报告标题统一称为“每日监控”。
- “分诊”只是系统内部能力，不作为页面、报告章节或独立流程名称。
- 新的活动工作流为 `/daily-monitor`；`/weekly-review` 退出活动流程。

### 3.2 历史归档

- `reports/weekly-check/` 中已有文件原样保留，只作为历史归档，不再生成新文件，也不进入 Pages。
- `reports/trigger-scan/` 中已有文件原样保留，只作为旧系统历史，不再作为 Pages 活动数据源。
- 新报告统一写入：

```text
reports/daily-monitor/
  daily-monitor-YYYYMMDD.md
  daily-monitor-latest.md
  daily-monitor-latest.json
```

- 同一日期重复运行覆盖当日快照和 latest，不创建 `-v2`。

## 4. 报告信息架构

报告开头只保留紧凑摘要，不单独形成第四个业务部分：

- P0 数量；
- P1 数量；
- 新增价格触发数量；
- 新增正式披露数量；
- 数据源、解析或模型异常数量；
- 数据截止时间和本次运行状态（正常/降级）。

正文固定为三部分。每部分的新待办按 P0、P1、P2 排序；持续状态和已解除事项紧随待办展示，不另建重复章节。

### 4.1 一、价格监控

包含：

- 首次进入明确价格区间；
- 首次接近价格边界；
- 首次越过“不追高”等警示线；
- 已触发条件的持续状态；
- 离开区间或条件解除；
- 行情获取失败、代码冲突或报价异常。

默认优先级：

| 情况 | 默认级别 | 通知行为 |
|---|---:|---|
| 首次进入明确复核价格带 | P0 | 通知一次 |
| 首次接近边界 | P1 | 通知一次 |
| 首次越过“不追高”等警示线 | P1 | 通知一次 |
| 条件持续不变 | P2/持续状态 | 不重复通知 |
| 离开区间/条件解除 | 已解除 | 通知一次 |
| 报价失败或代码冲突 | P1/待人工确认 | 首次故障和恢复时通知 |

距离触发边界较远、且状态没有变化的标的不逐条展开，只在摘要中统计。

所有措辞使用“价格条件已满足/接近，需要继续核验经营条件和 thesis 红线”，不得将价格触发表述为买入建议。

### 4.2 二、财报与正式披露监控

包含：

- 财报、年报、季报、中报；
- 业绩预告、盈利预警、业绩快报；
- SEC 10-K、10-Q、20-F、6-K、8-K 等目标配置允许的表单；
- 巨潮、HKEXnews 的重大正式公告；
- 正式披露的管理层、资本配置、并购、监管和重大经营事项；
- 未来 14 天内已知的财报或正式披露节点；
- DeepSeek 对新增正式事实与现有 thesis、看板、台账之间关系的判断。

新财报、年报、业绩预告或盈利预警至少为 P0。没有新增正式事实的重点标的不逐行展开，只在摘要中报告“已检查且无新增披露”的数量。

每条已验证事实必须保留官方来源 URL；没有官方链接只能标为线索或待人工确认，不能写成“已验证事实”。

### 4.3 三、其他监控

包含不能自然归入价格或正式披露的事项：

- 非披露类复检事件到期或未来 14 天到期；
- thesis、重点标的看板、标的跟踪台账和触发规则之间的覆盖缺口；
- 新研究报告给出明确价格带或复检节点，却没有登记触发规则；
- thesis 缺少下次检查时间或关键关注项；
- 台账复检日已过但状态未关闭；
- 达到 thesis 升级条件但没有结构化 thesis；
- 本地链接失效、代码不唯一、公司与披露主体无法映射；
- 正式数据源不可用、覆盖不完整或恢复；
- PDF 需要 OCR、正文提取失败；
- DeepSeek 超时、限流、JSON 校验失败或恢复。

完整性检查只报告缺口，不自动补录或改变本地研究状态。

### 4.4 跨部分去重

同一标的可以同时出现在多个部分，但每部分只保留自己的事实切片：

- 价格部分只说价格状态；
- 披露部分只说正式披露及其论文影响；
- 其他部分只说事件、完整性或系统问题。

“建议下一步”只放在影响最高的部分。其他部分使用交叉引用，不重复 thesis 分析、事实摘要或 workflow 推荐。

## 5. 数据源范围

### 5.1 一期正式披露源

| 市场 | 主数据源 | 用途 |
|---|---|---|
| A 股 | 巨潮资讯（CNINFO） | 公告发现、元数据、官方文件链接 |
| 港股 | HKEXnews | 公告发现、元数据、官方文件链接 |
| 美股 | SEC EDGAR | submissions/filing 元数据及正式文件 |

一期不做通用搜索引擎或全网新闻搜索。

### 5.2 备用源

AKShare 只作为备用适配层或异常时的线索来源，不取代官方源。AKShare 返回的事项必须能回到官方披露链接，才能标记为“已验证正式披露”；否则只能标为待核验线索。

### 5.3 价格源

价格监控沿用现有腾讯行情接口。若实施时需要替换或补充价格源，应作为独立变更评审，不借本设计自动扩大范围。

### 5.4 EDGAR 身份配置

SEC 公共数据接口免费且不需要 API Key。工作流通过 GitHub Actions Secret `EDGAR_IDENTITY` 配置真实、可联系的 User-Agent 身份，例如：

```text
AI Berkshire Research your-email@example.com
```

请求实现应低于 SEC 限速，目标控制在每秒 1—2 个请求，并包含退避、缓存和明确的 User-Agent。

## 6. 配置与运行状态分离

### 6.1 `data/triggers.json`

这是人工维护的声明式配置，保存：

- 标的身份和市场代码；
- 价格区间与事件；
- 本地研究链接；
- 正式披露源配置。

示例扩展：

```json
{
  "disclosure_sources": {
    "hkex": {"stock_code": "00700"},
    "sec": {"cik": "0001293451", "forms": ["6-K", "20-F"]}
  }
}
```

一个标的可配置多个市场披露源。`triggers.json` 仍遵守“人工修改、更新 `updated`、运行 `trigger_scanner.py --check`、推送前确认”的现有纪律，GitHub Actions 不自动修改它。

### 6.2 `data/monitoring-state.json`

这是机器维护的运行状态，保存：

- 各数据源的增量游标和最近成功时间；
- 已见公告 ID、文件哈希和处理状态；
- 各价格区间、事件的上次状态；
- 待重试披露；
- 数据源、提取器和模型的最近健康状态。

两个文件不得合并。原因是规则配置需要人工审查，而运行状态需要每日自动更新；合并会造成自动任务频繁改写人工规则，也会破坏现有触发规则的提交纪律。

状态更新使用原子写入；只有对应阶段成功后才推进游标。AI 或正文处理失败的披露必须保留为 pending，不能误记为已完整处理。

## 7. 正式披露标准化与去重

三个市场适配器统一输出以下核心字段：

```text
target_id
source
document_id
title
published_at
document_type
official_url
download_url
sha256
extraction_status
pages_used
```

去重顺序：

1. 官方公告/申报唯一 ID；
2. 下载文件的 SHA-256；
3. `target_id + 规范化标题 + 发布日期` 的保守组合键。

A/H 两地发布的同一材料可以合并成一个监控事项，但必须保留所有官方来源链接和市场身份。无法可靠判定为同一材料时宁可分别保留，不进行激进去重。

## 8. PDF 和正文处理

1. 公告文件下载到 GitHub Runner 的 `$RUNNER_TEMP`。
2. 对文本型 PDF 使用 PyMuPDF、`pdftotext` 或 pdfplumber 提取带页码文本。
3. 先按标题、目录、财务关键词和目标 thesis 问题筛选相关页，再把有限片段传给 DeepSeek。
4. 模型输出必须引用官方 URL、所用页码和事实置信度。
5. 只保存公告元数据、哈希、使用页码、引用事实、模型结构化结论和处理状态。
6. 运行结束后删除临时 PDF 和提取文本。
7. 扫描版或无法提取的 PDF 标记 `OCR_REQUIRED / 待人工确认`；一期不做 OCR。
8. 超大文件无法完整处理时，至少登记官方元数据和限制说明，不让模型补猜正文。

公告正文一律视为不可信提示词数据。系统提示明确禁止公告内容修改任务规则、调用工具、索取密钥、改变输出模式或执行代码。

## 9. DeepSeek 增量判断

### 9.1 调用时机

只在出现下列增量时调用 DeepSeek：

- 新的正式披露；
- 价格状态发生 `FAR → NEAR → TRIGGERED` 等变化；
- 登记事件状态变化；
- 新的 thesis/看板/台账/触发覆盖缺口；
- 数据源、正文提取或模型发生新故障或恢复。

持续不变的事项不重复调用、不重复通知。

### 9.2 输入范围

模型输入仅包括完成判断所需的最小上下文：

- 新增事实或状态变化；
- 对应标的的触发规则；
- 相关 thesis 摘要、红线和关键关注项；
- 看板/台账对应行；
- 官方来源链接和必要的带页码正文片段。

### 9.3 结构化输出

DeepSeek 输出 JSON，核心字段为：

```text
priority
why_now
verified_facts[] { fact, official_url, page, confidence }
thesis_impacts[]
next_workflow
needs_human_review
limitations[]
```

模型不得输出或驱动交易动作字段。`next_workflow` 只允许指向既有研究流程，例如 `/earnings-review`、`/news-pulse`、`/thesis-tracker`、`/thesis-drift` 或 `/portfolio-review`。

### 9.4 程序硬规则

程序先计算最低优先级，DeepSeek 可以升级，不能降级：

| 最低级别 | 硬条件 |
|---|---|
| P0 | 新财报/年报/业绩预告；潜在 thesis 红线；首次进入明确复核价格带；重大正式监管事项；复检已逾期 |
| P1 | 未来 14 天关键事件；首次接近价格边界；thesis 健康度 ≤6；重要经营/管理层/资本事项待核验；数据源或提取失败 |
| P2 | 无新增正式事实；价格或事件状态不变；既有条件仍未满足 |

附加约束：

- 没有官方来源链接，不得标为已验证事实；
- 正文提取失败，只能标为待人工确认；
- 价格变化不能自动改变 thesis 健康度；
- 模型不得自动修改事件、台账、看板、触发规则或仓位。

## 10. GitHub Actions 设计

### 10.1 触发条件

工作流使用：

```yaml
on:
  schedule:
    - cron: "30 17 * * 1-5"
      timezone: "Asia/Shanghai"
  workflow_dispatch:
```

`workflow_dispatch` 提供 `commit` 和 `notify` 开关，用于不提交、不通知的人工验证。工作流增加 `concurrency` 防止定时与手工运行重叠，并设置合理的 `timeout-minutes`。

### 10.2 执行顺序

1. Checkout 仓库；
2. 安装 Python 3.12 和缓存依赖；
3. 安装每日监控专用依赖；
4. 校验 `triggers.json`、`monitoring-state.json` 和披露源配置；
5. 运行确定性的价格与登记事件扫描；
6. 从巨潮、HKEXnews、SEC EDGAR 获取并标准化新增披露；
7. 与 `monitoring-state.json` 比对，产生增量集合；
8. 在临时目录下载并提取新增文件的必要内容；
9. 从 thesis、看板和台账构造最小研究上下文；
10. 调用 DeepSeek，并校验 JSON 输出；
11. 应用程序优先级下限和证据规则；
12. 渲染 Markdown 与 JSON 每日监控报告；
13. 对新增 P0/P1、已解除事项、首次故障和恢复发送通知；
14. 更新 `monitoring-state.json`；
15. 仅提交 `reports/daily-monitor/` 和 `data/monitoring-state.json`；
16. 显式触发 Pages 重建。

工作流不得自动提交 `data/triggers.json`，也不得提交临时文件、PDF 或正文。

### 10.3 配置

GitHub Actions Secrets：

- `DEEPSEEK_API_KEY`；
- `EDGAR_IDENTITY`；
- 现有通知渠道密钥，如 `SERVERCHAN_SENDKEY`。

GitHub Actions Variable：

- `DEEPSEEK_MODEL`，避免把模型名称硬编码到程序中。

如未配置 DeepSeek Key，工作流仍生成确定性价格/事件/披露元数据报告，并明确标为降级运行。

## 11. 失败与恢复策略

### 11.1 部分数据源失败

- 单个市场失败时继续处理其他市场和价格监控；
- 在“其他监控”登记首次故障；
- 不推进失败数据源的增量游标；
- 恢复后补抓缺失区间，并发送一次恢复通知。

### 11.2 DeepSeek 失败

- 超时、限流、空响应或非法 JSON 时退避后重试一次；
- 仍失败则生成确定性降级报告，标记“AI 判断待补充”；
- 未完成 AI 判断的披露保留 pending，下一工作日重试；
- 不因模型失败丢弃正式披露或价格状态事实。

### 11.3 提取失败

- 文本型 PDF 解析失败时标记待人工确认；
- 扫描型 PDF 标记 `OCR_REQUIRED`；
- 不把解析失败的内容交给模型猜测；
- 不推进“正文已完成处理”的状态。

### 11.4 工作流最终状态

降级报告应先成功写出并允许 Pages 更新；随后健康门根据严重性把 Actions 标为失败或警告。这样用户既能在页面看到故障说明，也能从 Actions 红灯发现自动化异常。

---

## 12. 通知策略

只对状态变化通知：

- 新出现的 P0；
- 新出现的 P1；
- 首次价格触发、首次接近、首次警示；
- 条件解除或事项恢复；
- 数据源、正文提取或模型的首次故障和恢复。

不通知：

- 与上一工作日完全相同的持续状态；
- 距离触发条件较远的价格；
- 无新增事实的 P2；
- 同一事项在同次运行中的跨章节重复描述。

通知只给摘要和 Pages/官方来源链接，不嵌入完整公告正文。

---

## 13. 安全与合规边界

1. 下载只允许巨潮、HKEXnews、SEC 及明确配置的官方域名，并校验重定向目标。
2. Secrets 不写日志、不写报告、不进入模型输入。
3. 日志中避免输出完整公告正文和完整 DeepSeek 请求。
4. 临时目录在运行结束时清理。
5. 所有外部内容均作为不可信数据处理，不执行其中的指令、链接代码或附件宏。
6. 输出固定包含“用于学习与研究，不构成投资建议”。

- 不再在构建时组合 trigger-scan latest 和 weekly-check latest；
- 历史目录继续留在仓库，但不作为活动页面入口。

## 16. 验收标准

1. 工作流在周一至周五 17:30（Asia/Shanghai）自动运行，周末不运行。
2. Pages 只有一个活动入口“每日监控”，报告只有价格、正式披露、其他监控三部分。
3. 相同状态不会连续重复通知；条件变化、解除和恢复各通知一次。
4. 新披露只处理一次；失败事项可以重试且不会丢失。
5. DeepSeek 或单一市场接口故障时，确定性价格和事件监控仍可输出。
6. 每条“已验证事实”均有官方来源；提取失败不会被模型补猜。
7. DeepSeek 不能降低程序优先级，也不能作出或执行交易/仓位决定。
8. `triggers.json` 保持人工维护，`monitoring-state.json` 由自动化独立更新。
9. `reports/weekly-check/` 和现有 `reports/trigger-scan/` 历史文件保持不变。
10. 仓库与日志中没有 PDF、完整公告正文、模型完整上下文或密钥。
11. 新技能和多客户端生成产物一致，旧“监控与周检”文案、旧运行时间和 Pages 组合逻辑不再作为活动配置存在。
